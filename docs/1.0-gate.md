# Seven 1.0 Gate

## Objetivo

A Seven 1.0 somente pode ser publicada quando a cadeia de desenvolvimento,
compilacao, runtime e release corrente for verificavel sem depender do
compilador nativo de transicao.

Este documento complementa `docs/production-gate.md`. O gate de 0.x prova a
fundacao existente; o gate 1.0 exige que essa fundacao seja a propria cadeia
operacional do produto.

## Regra principal

A release 1.0 precisa seguir este caminho:

```text
bootstrap minimo auditavel
        -> Seven-0
        -> Stage 1
        -> Stage 2
        -> Stage 2 self
        -> compilador/runtime corrente
        -> CLI + conformance + native + WebAssembly
        -> release Windows/Linux
```

Nenhum workflow ativo da versao corrente pode voltar para
`seed/native/final/v1` para fornecer o compilador distribuido.

Artefatos historicos podem continuar existindo para verificacao de releases
imutaveis antigas, mas ficam fora da fronteira operacional da 1.0.

## Gates obrigatorios

### G01 - Bootstrap deterministico

- Seven-0 recompila a si proprio byte a byte.
- Stage 2 recompila a si proprio byte a byte.
- a proveniencia registra executor, entrada, saida e SHA-256.

### G02 - Compilador corrente self-hosted

O compilador que entra no pacote de release deve vir da cadeia self-hosted
corrente. Nao e suficiente gerar `seven.svbc` com um executavel de transicao e
depois comparar duas saidas desse mesmo executavel.

### G03 - CLI self-hosted

A cadeia corrente deve provar o contrato publico real:

```text
seven --version
seven check
seven build
seven run
seven web build
seven doctor
```

Ferramentas que permanecerem em preview devem ser declaradas explicitamente
como preview e nao bloqueiam a 1.0.

### G04 - Conformance

Todos os casos `conformance/**/valid/*.sev` sao aceitos pelo compilador
self-hosted e todos os casos `conformance/**/invalid/*.sev` sao rejeitados.

### G05 - Backend x64 sem stubs estaveis

Nenhuma operacao declarada estavel pode terminar em stub que devolve valor
ficticio. Operacoes nao implementadas devem ficar fora da superficie stable ou
falhar explicitamente.

### G06 - Runtime nativo de rede

Windows x64 e Linux x64 precisam implementar de verdade, no backend nativo:

```text
sys_tcp_escuta
sys_tcp_aceita
sys_tcp_le
sys_tcp_escreve
sys_tcp_fecha
```

Apenas declarar esses contratos em `target.sev` nao conta.

### G07 - HTTP nativo E2E

O teste inicia um binario AOT produzido pela Seven, abre um socket real,
realiza uma requisicao HTTP e valida resposta, fechamento, limites e erro.

Executar o mesmo programa pelo `genesis-host` continua sendo uma boa prova de
linguagem/SVBC, mas nao substitui a prova do backend nativo.

### G08 - WebAssembly

Aplicacoes semanticamente diferentes geram modulos distintos e o E2E valida
DOM, eventos, CSS, armazenamento e handlers reais.

### G09 - Filesystem, console, Bytes e memoria

As capacidades usadas pelo proprio compilador precisam estar cobertas no
runtime nativo, sem fallback silencioso para host de transicao.

### G10 - Stable versus Preview

Antes do tag 1.0, a superficie publica e congelada em duas classes:

- stable: contrato de compatibilidade mantido na serie 1.x;
- preview: pode evoluir sem promessa de compatibilidade equivalente.

### G11 - Release reproduzivel

Dois rebuilds limpos da mesma revisao devem produzir compilador self-hosted
equivalente e hashes deterministas para os artefatos onde o formato permite
reprodutibilidade byte a byte.

### G12 - Pacotes oficiais

O pipeline valida:

- Windows x64 MSI;
- Linux x64 tar.gz;
- extensao VS Code VSIX;
- SHA-256;
- layout instalado;
- execucao do compilador instalado;
- desinstalacao/limpeza quando aplicavel.

### G13 - Seguranca

Os decoders e parsers precisam rejeitar entradas truncadas, tamanhos fora de
limite, bytecode invalido e caminhos inseguros. Testes de regressao cobrem as
fronteiras publicas da VM, filesystem, HTTP e WebAssembly.

### G14 - Compatibilidade 1.x

A especificacao de sintaxe, tipos, efeitos, memoria, ABI e SVBC stable deve
estar versionada. Alteracoes incompatíveis exigem uma politica explicita de
migracao ou uma futura major.

### G15 - Release blockers

Nenhuma issue classificada como bloqueadora de release pode permanecer aberta
no momento do tag 1.0.

## Estado encontrado antes do hardening

Na `main` anterior a este gate:

- Stage 2 alcanca fixed point;
- Stage 2 compila e executa aplicacao nova;
- WebAssembly possui E2E real;
- PE32+ e ELF64 sao gerados pelo backend AOT;
- o E2E HTTP do Stage 2 ainda roda hospedado pelo Genesis;
- workflows ativos ainda usam `seed/native/final/v1`;
- o backend x64 ainda possui chamadas a `x64_syscall_stub_nulo`;
- `target.sev` declara TCP, mas o dispatcher nativo ainda nao possui modulo de
  rede correspondente;
- a release 0.2.2 ainda distribui o compilador de transicao 0.2.0.

## Criterio de publicacao

A versao so recebe o tag 1.0 quando todos os gates G01-G15 estiverem verdes no
mesmo commit de release.
